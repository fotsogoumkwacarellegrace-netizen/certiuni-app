# Livrable 3 : Diagrammes de Flux de Données (Data Flow) - CertiUni

Ce document décrit le parcours technique de la donnée lors des deux processus critiques du système : l'émission de diplômes en masse et la vérification publique.

---

## 1. Flux 1 : Processus d'Émission (Ingestion -> Signature -> Stockage S3)

```mermaid
sequenceDiagram
    autonumber
    actor Admin as Admin Université (ADMIN_UNIV)
    participant API as API Express (Backend)
    participant Queue as File Redis (BullMQ)
    participant Worker as Worker Puppeteer
    participant S3 as Stockage S3 / MinIO (WORM)
    participant DB as PostgreSQL (Core Ledger)

    Admin->>API: 1. Upload fichier Excel/CSV + Paramètres
    API->>API: 2. Vérification JWT & Droits Tenant (`university_id`)
    API->>DB: 3. Création des entrées Étudiants (si absents)
    API->>Queue: 4. Empilement des tâches de génération (Batch)
    API-->>Admin: 5. Réponse 202 Accepted (Job ID)

    par Traitement Asynchrone
        Worker->>Queue: 6. Dépilement de la tâche
        Worker->>Worker: 7. Calcul du Hash SHA-256 Canonique
        Worker->>Worker: 8. Génération du QR Code PNG
        Worker->>Worker: 9. Rendu HTML/CSS -> PDF (Puppeteer)
        Worker->>S3: 10. Upload du PDF certifié (Bucket WORM)
        Worker->>DB: 11. Insertion Diplôme (status: VALID, hash, pdf_s3_key)
        Worker->>DB: 12. Audit Log (Action: BATCH_CERTIFICATE_ISSUED)
    end
    2. Flux 2 : Processus de Vérification Publique (Scan QR Code / Hash)
    sequenceDiagram
    autonumber
    actor Public as Recruteur / Public
    participant Front as Frontend Web (Angular)
    participant API as API Express (`/api/v1/verify`)
    participant Redis as Redis Cache / Rate Limit
    participant DB as PostgreSQL (Core Ledger)

    Public->>Front: 1. Scan QR Code ou Saisie manuelle du Hash
    Front->>API: 2. Requête GET `/api/v1/verify/:hash`
    API->>Redis: 3. Check Rate Limit IP (Max 30 req/min)
    
    alt Limite dépassée
        Redis-->>API: Dépassement détecté
        API-->>Front: HTTP 429 Too Many Requests
    else Limite autorisée
        API->>DB: 4. Requête SQL SELECT par `hash_sha256`
        
        alt Hash trouvé (Statut: VALID)
            DB-->>API: Données du diplôme
            API->>DB: 5. Insertion dans `verification_logs` (Result: VALID)
            API-->>Front: HTTP 200 OK (Métadonnées + Statut Vert)
        else Hash trouvé (Statut: REVOKED)
            DB-->>API: Données du diplôme révoqué
            API->>DB: 5. Insertion dans `verification_logs` (Result: REVOKED)
            API-->>Front: HTTP 200 OK (Motif Révocation + Statut Rouge)
        else Hash introuvable
            DB-->>API: Aucun résultat
            API->>DB: 5. Insertion dans `verification_logs` (Result: INVALID)
            API-->>Front: HTTP 404 Not Found (Statut Gris / Invalide)
        end
    end
    ---

### 3. COMMENT SAVOIR si votre livrable est correct ou s'il y a une erreur ?

Pour valider que votre livrable est conforme et prêt pour les développeurs :

#### A. Validation visuelle immédiate (Dans VS Code)
1. Installez l'extension VS Code nommée **Markdown Preview Mermaid Support** (ou **Markdown Preview Enhanced**).
2. Ouvrez la prévisualisation de votre fichier (`Ctrl + Shift + V`).
3. **Résultat attendu :** Les blocs de code `mermaid` doivent se transformer automatiquement en **diagrammes visuels fluides** avec des flèches et des composants distincts. S'il y a une erreur de syntaxe, un bloc d'erreur rouge s'affichera à l'écran.

#### B. Les 3 règles de contrôle d'architecture (Pour éviter les erreurs conceptuelles)
* **Contrôle 1 (Composants) :** Le schéma doit faire apparaître distinctement le serveur API, la base PostgreSQL, le stockage S3 et la file d'attente Redis/BullMQ.
* **Contrôle 2 (Garde-fous) :** Le flux de vérification doit obligatoirement inclure le passage par le **Rate Limit Redis** avant d'interroger la base de données.
* **Contrôle 3 (Gestion des échecs) :** Le flux de vérification doit montrer les 3 cas de figure de retour : Validé (Vert), Révoqué (Rouge) et Introuvable (Gris/404).
